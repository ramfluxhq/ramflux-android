# Changelog

## [Unreleased]

- Agent cards held-operation fixes: an operation that started on a card runs to its answer without cancellation, so a tap, slot answer or submit whose call reached the core gets its real reply (absorbed into the held tree) or a failure with an unknown outcome and a "result unknown" notice, never a "tap again"; only operations that never started are dropped. Operations of a signed-out account are dropped without asking for a tap again (a submit fails with no outcome). Sign-out and removal run the purge and the close without cancellation and re-admit the account when the core still lists it unlocked, so a caller that goes away cannot leave an open account with its cards shut; account selection checks the list under the account's gate. A dropped card input says "input not applied" at most once every five seconds per card.

- Agent cards queue hand-off fixes: each card queue instance has its own consumer, and a consumer that ends unmaps only its own queue, so a call made while a drain finishes is never lost or applied out of order; an `input` that finds an `input` for the same control at the tail of the queue replaces it, so typing cannot fill the queue, and a tap, tab change or slot answer that finds the queue full or whose consumer was cancelled answers `stale_dropped` (the chat asks for the tap again, also when the call failed); host slot answers and the submit of a pending action go through the same per-card queue, so the runtime sees them in the person's order; the event stamp carries the runtime session and signed version as well as the tree version and edit sequence, so a stamp from before a reopen never matches; sign-in, sign-out, removal and lock of one account run one at a time, and a failed sign-out or removal re-admits the account's cards only when the account is still listed and unlocked, so a second sign-out cannot undo the first.

- Agent cards event order fixes: the events of one card go through a FIFO queue with one consumer, so they reach the runtime in the order the person made them; only consecutive `input` events for one control at the head of the queue are replaced by the newest, never across a tap; an `input` or `activate` on an older tree is re-sent only while its control is still the same node kind and `input_pointer` as in the tree the person saw, and an `activate` only when every later step came from an `input` queued before the tap, otherwise it answers `stale_dropped` and the chat shows a "tap again" notice (en, zh-CN); a signed-out account is remembered, so a late `show` creates no entry and opens no session until the account is unlocked or switched to again; link and approval answers go through the same absorb as event replies so the held tree and stamp chain stay in step with the core.

- Agent cards input fixes: fast typing, toggles and picks no longer leave a control showing a value the runtime does not hold. An `input` that follows the card's own earlier events is re-sent with the token of the current tree (the pool keeps the chain of stamps its own replies produced, and it ends on any outside change), only the newest `input` per control is sent while one is in flight, Activate, SelectTab and modal events keep the strict stamp check, and every dropped `input` answers `stale_dropped` so the TextField, CheckBox, ChoicePicker and Slider revert to the tree value. A call that waited on the lock of an account that signed out no longer opens a runtime session (`retired` entry), and a modal the runtime still holds open after a cover is closed there when the card is usable again.

- Agent cards security audit fixes: card windows (the modal sheet, the link sheet, the approval confirmation and the date and time pickers) are not drawn above the app lock cover and a suspended or covered card closes its modal; a Slider whose bounds or value overflow a Float draws disabled instead of crashing the conversation; a host event carries the tree version the person saw and is dropped when the held tree moved on; the modal sheet shows the AI marker and a "From the agent" header on the plain card surface so it cannot pass for the approval sheet; Button labels, validation messages and the chart unit go through the untrusted-text filter; a malformed icon path draws the empty box; the cards are suspended on every cover even when already marked suspended; sign-out and account removal dispose the account's card sessions and drafts (`CardSessionPool.forget`); a number field keeps only finite values; `CardNode` no longer prints its attributes; the link sheet scrolls and shows the host on its own line.

- Agent cards lock fixes: an app lock refusal covers the screens at once, before the cards are suspended, so a busy card call cannot delay the cover; the cards resume after any later lock read that finds the lock open; a card re-opens only on the explicit inactive refusal or a closed-account failure, so a transient failure keeps its session and draft; re-opening a card at the maximum no longer evicts an unrelated card.

- Agent cards review fixes: cards stay suspended behind the app lock and resume only when the cover is released (a lock refusal suspends them first); a suspend that fails because the account closed keeps the held tree and re-opens the card on release; reading card states no longer reorders the least-recently-used cards; the timeline disposes the oldest card by creation time and releases its cards when it leaves a conversation; a slider whose bounds hold no whole number stays disabled; card links open only over http or https; a TextField keeps the typed text on its own echoes; a card answer with an unknown outcome shows a failure notice.

- Agent card Slider sends its released value as a whole number inside its bounds (the runtime rejects fractions), and the card conformance compares `request_id` texts by their parsed JSON, so trees with host slots (Image, Approval) match the core fixtures; failed host slots are written in full to `card-host-slots.json`, and real-run flow 21 scrolls the gallery to the top before it looks for the Dark switch.

- Card gallery conformance: the gallery applies the runtime's callback payload (not the `{session, payload}` envelope), so open batches apply to the empty tree; a JVM test applies every host fixture to `CardTree.EMPTY`. Check A still records when a batch fails, checks B and C still run, every failure carries expected and actual excerpts, the RTL row reads NOT AVAILABLE, and flow 21 captures five dark gallery pages. The native build no longer packages the ramflux-card copy of `libramflux_sdk.so` in the APKs.
- Card gallery and conformance (test builds only): `card-fixtures/` holds the core host fixtures at the pinned revision (`scripts/sync-card-fixtures.py`, SHA-256 `MANIFEST.json`, refused on drift). The realrun build type alone has the gallery (`CardGalleryActivity`, not exported, not in the debug or release manifest): it draws every fixture and scenario through the card renderer from the standalone card runtime, and Run conformance checks the opened trees against the core's expected trees, the renderer's kind coverage and the interactive events (self-consistency with a fresh runtime read), writing `card-conformance.json`. The card runtime binding `libramflux_card_fixture.so` is built only with `RAMFLUX_CARD_FIXTURE=1 scripts/build-native.sh` and packaged for that build type only. Real-run flow 21 runs the gallery and keeps the report.
- Agent cards run on the core card runtime: the native build enables `card-runtime` (`negotiate` advertises `card_runtime`), `core/data/cards/` holds the typed `card.session.*` client, the atomic tree model and a per-account session pool (2 resumed, 24 held, LRU; suspended on background and app lock, resumed on foreground). The client-side surface parser and `surface.action` submit are removed; the timeline draws each card with the native renderer below.
- Agent cards render natively: the new module `:feature:cards:renderer` draws all 20 card kinds (Text, Icon, Row, Column, List, Card, Tabs, Modal, Divider, Button, TextField, CheckBox, ChoicePicker, Slider, DateTimeInput, Image, Approval, Task, Chart, Table) from the card runtime tree, with the design-kit tokens, the tree's direction and format locale, and the lifecycle states of the render spec (generating, waiting for confirmation, closed, updated, out of sync, over limit, suspended, fallback text). Inputs, submit, tabs, modal and the approval decision go through `card.session.*`; a link opens the system browser only after the runtime answers `opened`, through a sheet that shows the full URL; an approval stops at "Waiting for confirmation" until the signed update. Image draws its unavailable state until the runtime delivers image bytes. The app locale and theme reach the card runtime on open and on change.
- Group system events are centred, named lines: a service row the client cannot display no longer draws an own bubble with the "cannot be displayed" text, and a peer without a resolved name is shown as "Member", never its device id (RFGUI-72). The fallback line for a service row reads "Group updated".
- App lock (off by default). Settings > Privacy > App lock switches on the account's app lock and picks the time away after which it applies (immediately, 1, 5, 15 minutes or 1 hour). While the lock is on, returning to the app shows a cover that asks for the six-digit account code; nothing of the account shows until `account.app_lock.state` has been read, and an unreadable state keeps the cover up with a retry. Any `app_locked` refusal shows the same cover. Banners stay hidden while the lock is on or unread. The code is never stored on the phone. The biometric row is shown disabled until the core offers presence unlock. The cover is `AppLockCover` in `:feature:onboarding:impl`, the page is `SettingsPage.APP_LOCK` in `:feature:settings:impl`, and the state is `ClientSnapshot.appLock` in `:core:data`.
- App lock cover stays up when the session fails: a failed resume or suspend after the lock was on, engaged or unread no longer drops the cover (the failed phase went to the shell, so screens such as the contact card showed data without the code). The cover shows the retry, and the retry reopens the session. The cover keeps the typed code while it reads which account is locked and then unlocks once, keyboard and D-pad focus cannot enter the shell while it is up, saving the app lock page refreshes the session's lock state at once, and `lockEngaged` is volatile.

- App lock cover: back on the lock form no longer pops the open conversation underneath. The cover's back handler was composed once and kept its first place in the dispatcher's order, so a chat opened after the app started handled back first and left the Messages list behind the form (the open chat was gone after the right code); the handler now enters the composition only while the cover is up (`CoverBackGuard`), so it registers last and takes back. The shell under the cover is also hidden from accessibility services and UI automation (`Modifier.hiddenWhileCovered`); `FLAG_SECURE` is unchanged. Real-run flow 20 turns the lock off when a phase fails and clears a stale lock at the start of a phase.
- The open direct conversation keeps the peer's name in its header: the header resolves the peer through the same keys as the conversation list (the route's peer and the participants, so a conversation without a direct route is named too), and a session phase change (app lock, return to the app) keeps the last named title until the re-read names it again, instead of showing the generic title.
- App lock release no longer leaves an empty shell: the engaged lock closes the account in the SDK, so the screens read behind the cover saw no active account and never read again. When the account code opens the lock the session starts a new generation, and open screens (Messages, the open conversation and the rest) read again on the same navigation stack, so the same account and conversation come back. Back on the lock form only hides the keyboard and keeps the typed code.
- App lock cover now follows each account's own lock state: closed and restoring accounts are read with `account.app_lock.state` and covered only when their lock is on or the read fails, and an open without an unlocked account no longer sends the foreground call, so a device that never enabled the lock keeps onboarding, account-locked unlock, restore and forget account as before.
- App lock (off by default). Settings > Privacy > App lock switches on the account's app lock and picks the time away after which it applies (immediately, 1, 5, 15 minutes or 1 hour). While the lock is on, returning to the app shows a cover that asks for the six-digit account code; nothing of the account shows until `account.app_lock.state` has been read, and an unreadable state keeps the cover up with a retry. Any `app_locked` refusal shows the same cover. Banners stay hidden while the lock is on or unread. While the cover is up, dialogs, bottom sheets and menus are not shown, an open dialog or sheet is dismissed, and the window refuses capture (`FLAG_SECURE`), so the recents preview shows nothing. The code is never stored on the phone. The biometric row is shown disabled until the core offers presence unlock. The cover is `AppLockCover` in `:feature:onboarding:impl`, the page is `SettingsPage.APP_LOCK` in `:feature:settings:impl`, and the state is `ClientSnapshot.appLock` in `:core:data`.

- SDK pin moved to core release v0.2.9 (`30d0f9a7`): the method policy gains `attachment.transfer.list`, `attachment.transfer.pause` and `attachment.transfer.resume` (generated repository methods, not used by the app yet). No method was removed and the contact verify CAS descriptor is regenerated from the pinned commit.
- SDK pin moved to core release v0.2.8 (`731de8bf`): the app lock lifecycle and fences, the phone call media engine lifecycle, unconfirmed group invitations, idempotent repeated read receipts, the diagnostic support key catalogue and the signed reach record methods. The method policy gains `account.app_lock.lifecycle`, `account.app_lock.lock`, `conversation.start`, `contact.requests.reply`, `account.reach.get` and `account.reach.set` (generated repository methods, not used by the app yet), and `call.media.session` is no longer allowed across the bridge (the app never requested it: the call engine refuses first). The real-run flow 10 note now states what the flow observes on the language screen (the system-language row is listed or did not appear within 10 s).
- The data saver line appears on the delivery page: `ACCESS_NETWORK_STATE` is declared (by `:push:impl`; Firebase messaging expects it too), the removal marker in `:core:media` now covers only `WAKE_LOCK`, and the permission guard lists the new permission. `WAKE_LOCK` stays removed until the wake path shows it is needed.

- Firebase Cloud Messaging in `:push:international:fcm` (Firebase BOM 35.1.0, `firebase-messaging` only; the Play services client libraries come with it): `FcmPushProvider` starts `FirebaseApp` by hand from values that the build reads from the `google-services.json` named by the Gradle property `ramflux.firebase.configFile` (the entry for the app's application id; no property, no readable file or no matching entry means "not configured" and the build still succeeds; the Google services plugin is not applied and the file is never committed). The token stays in memory and is never logged. `PlayServicesStatus` maps missing, outdated, disabled and unusable Play services to reasons the delivery page shows. The manifest turns off automatic start, analytics, the advertising id and default data collection and removes the Firebase init provider. The messaging service is on the service allowlist with the new type `none` and brings only `com.google.android.c2dm.permission.RECEIVE`. Licence notices for Firebase and the Play services libraries are in the open-source notices.

- The delivery page has a local self-test: whether the readable settings are in order, a generic test message notification posted five seconds after the tap, and a test ring on the calls channel after ten seconds (it takes over a locked screen where Android allows it). The person locks the phone, then confirms what they saw; the result is not stored or sent. `USE_FULL_SCREEN_INTENT` is now declared by `:push:impl`.

- Delivery guidance triggers. A one-time bottom sheet "Make sure messages arrive on this phone" appears when the person leaves the permission screen with notifications allowed and either this brand has a required step or a required standard setting is off (at most three steps; "Not now" is final, and it is never shown on launch). The conversation-list banner slot raises one delivery banner at a time for a hard problem (message or call channel off, calls cannot take over the lock screen, background use restricted, standby bucket restricted, Play services unusable), each problem once per seven days and never while notifications are off (the permission banner covers that). After the person force-stops the app from the system, the next launch shows "Ramflux was stopped. Messages that arrived meanwhile were not announced." once per stop (Android 11 and later, from the process exit records).

- Settings has a "Message delivery" page (`DeliveryRoute`, `:push:impl`): the background-delivery status, the phone brand and Android version, and live readings of the standard settings that decide whether a wake arrives (notifications, message and call channels, full-screen calls, battery optimisation, background restriction, standby bucket, data saver, app hibernation, battery saver), re-read every time the page returns to the front. Brand steps come from the compat module; a step whose only targets are vendor screens that this phone does not have is not offered. Settings Ramflux cannot read are labelled "Not checked by Ramflux" with an "I've done this" mark that is never shown as a check and is dropped when the Android version or build changes. The page opens system screens only through `SafeSettingsLauncher` and counts the tier that opened per step. The battery row opens the system list of optimised apps; `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is not declared. The local store (`push-delivery` preferences) holds only confirmations, counters and timestamps.

- Per-brand delivery guidance (`:push:international:compat`): the device identity from the public build constants, a brand registry (HONOR before HUAWEI, every specific brand before the stock fallback) and one file for each of the twelve brand families (AOSP, Samsung, Xiaomi, Huawei, Honor, OPPO/realme/OnePlus, vivo/iQOO, Motorola, Sony, Nothing, Tecno/Infinix/itel, ASUS) with their steps and the vendor settings screens that may open them, the vendor packages as manifest `<queries>`, and the step and brand texts in English and Simplified Chinese. `SafeSettingsLauncher` (`:push:impl`) opens a screen only after resolving it (explicit components must be exported), skips what is missing or refused, falls back to the app-details page and never throws. The resource guard accepts dotted class names as stable ids. The vendor screens are unverified until a device has opened them.

- Notification channels follow the delivery design: `messages` is high importance (heads-up), `calls` is high importance with the default ringtone, ringtone audio attributes, vibration and a public lock-screen version, the new `missed_calls` is default importance and `system` is low importance and silent. A channel keeps the importance it was created with, so only installs that create the channels now get these settings (the `.dev` application id gives developers fresh channels). `USE_FULL_SCREEN_INTENT` is now declared, so the incoming-call row on the permissions page no longer always reads denied on Android 14 and later; the permission guard lists it.

- New top-level `push/` tree for background delivery: `:push:api` (interfaces and value types), `:push:impl`, and the international edition modules `:push:international:compat` and `:push:international:fcm`, with a README per level and a reserved `push/china/`. The Gradle property `ramflux.edition` (default `international`, in `gradle.properties`) selects the edition modules `:app` links; any other value fails configuration with "edition not implemented". `FcmPushProvider` is a placeholder that reports "not configured"; no Firebase dependency is linked. The permission guard scans `push/` and accepts the service type `none` (a service that is not a foreground service), the architecture guard keeps Google, Firebase and Play services classes inside `push/international/fcm` and checks the push module dependencies, and the resource guard covers the push modules; CI runs their unit-test tasks.

- The debug build has its own application id, `org.ramflux.android.dev` (launcher label "Ramflux Dev"), so debug, real-run (`.realrun`) and release (`org.ramflux.android`) install side by side with separate Keystore keys, notification channels and data. The native emulator smoke run installs, tests and uninstalls the new package and its `.dev.test` instrumentation package.

- A message that arrives while the app is in front is announced by an in-app banner drawn in the activity's own window (sender name and a one-line preview of at most 80 sanitised characters; fixed texts for calls, system events and media; about four seconds, tap opens the conversation, swipe up dismisses, a newer message replaces it). There is none for the open conversation, a muted conversation or the user's own message, and nothing is posted to the system in front. The banner host is kept out of autofill, content capture and (API 34+) non-tool accessibility services and announces through a polite live region; its state is never saved or logged. Every build turns off the Overview screenshot (API 33+) and content capture for the activity before content is set.
- A refused request no longer shows a bare number: one shared mapping turns the SDK's typed status name and `reason_code` into the text of every screen (the code, then the name and reason token, for example "Read failed (code 16, UsernameDirectoryRefused: directory_unavailable)"), and a reason the app has words for is shown in words (a node without a username directory says "Usernames are not available on this server yet.").
- SDK pin moved to the core's `next` head `5d117366` (runtime expiry and preemption, backup restore keeps attachment ownership, a read receipt emits one typed `message.updated` update so the sender's row carries Read): the username directory trust pin is passed in the open config (provisioned by the build from `ramflux.usernameDirectory.*` Gradle properties, and by the real-run script from the node facts), refusals use the SDK's typed `name` and `reason_code` and every status 0-31 is named from the generated header table, a group chat never asks for typing focus (a refusal is tolerated silently), the debug and real-run builds turn on the SDK diagnostic log and the real-run script copies it from the phone after each invocation, and a failed suspend is still followed by a resume (the SDK now rolls it back as a whole).
- The real-run script exits non-zero whenever the flow table holds a FAIL row or the instrumentation did not run to its end, and the table states an overall verdict.
- SDK pin moved to the core's `next` head `f2f466be2`: a contact re-added from its card keeps the pinned node fingerprint and a receive error no longer stops the apply pass (media send, later events and group invitations after a card exchange), the attachment contract is documented (the client already enables, prepares, streams and sends `prepares` as it describes), no plaintext attachment copy stays in the SDK after a send, agents call like people, and the app-lock methods enter the policy (not used by the app yet).
- SDK pin moved to the core's `next` head `14e38cda6`: suspend and resume, prompt-free cold open through the device-bound key, read receipts with a derived route, conversation names, leave group, the group invitation topic, username methods on phones and the SDK-verified AI marker.
- Returning from the background or relaunching asks for nothing: the client is suspended in the background and resumed on return (same session, screens and draft kept), and a new process waits while the SDK reopens the account through its device-bound key. The code is still asked after an explicit lock or sign-out, at set-up, restore and to change it. The SDK data root is a dedicated private directory.
- The AI marker appears wherever a person is shown (contacts and requests, the conversation list, the chat header, group members and the authors of group messages); agents are otherwise shown exactly like people.
- Direct conversations take their names from the SDK; group members and the authors of group messages are named from contacts instead of showing a device id. Group service rows (member added, name changed, ...) are centred lines, not undisplayable bubbles.
- Groups: leave a group (every member but the owner); invitations arrive live through `group.invitation`; the invitation buttons and the create actions carry test tags.
- Usernames: Privacy shows this account's username or the directory's typed refusal, and Contacts adds a contact by `@name`.
- Settings keeps the account and its actions usable while it refreshes; a tap on Lock right after opening the page was dropped before.
- Real run: the flow table and the instrumentation agree (a FAIL fails the test, a dead process or failed test is recorded as FAIL), a failing flow leaves a UI dump, every invocation starts from a stopped app, flows 03 and 07 fail on any prompt, and new flows cover the read receipt, an invitation from a non-contact with leaving, and usernames. Flow 09 waits for the create action that is laid out.

- SDK pin moved to the core's `next` head `e39111de5`: phone attachment send, own replies and the invitation list fixed in the SDK; account list with locked accounts, the unlock wait, sign-out and local removal; card session methods in the policy.
- Groups: a contact is added by its principal id alone (an explicit root made the SDK read the principal id as a device id, code 16); a new group opens the conversation its creation reply names, and opening a listed group asks the group's metadata before history.
- Accounts come from the SDK's `account.list` (locked ones included); the app's own account registry is removed. Settings signs the account out and removes it from this phone.
- The wait after wrong account codes is read from the SDK's `retry_after_ms`.
- Contact verification reads the SDK's `verificationState` reply field, so a successful verify is no longer reported as an unknown outcome.
- The composer draft survives background and lock: a session change while the draft was still being restored no longer erases the sealed draft.
- Own replies use the SDK's `is_own`; the client-side author-device workaround is removed.
- Debug trace: one start line per process, the sink is volatile, the suite marks flows under the trace tag directly, and the confirmation trace logs at warning level.
- Debug and realrun builds also write the trace to a private file that `scripts/realrun.sh` copies to `app-trace.txt`, because the test phone keeps only part of an app's own log lines.
- Groups: after an add the member list is shown again, and a finished change always clears the busy state.
- Chat: a send refused for a missing contact card (`authority_unavailable`) is shown as not sent with a retry and a hint to exchange contact cards, not as offline; the keyboard closes before the attach menu opens.
- Real run: each invocation exits non-zero when one of its own flows fails; new flows cover the group image, the invitation list, sign-out and removal from the phone.
- Live updates: the SDK's account journal is followed through `bus.subscribe`, so conversations and account state update without a manual refresh.
- The outbox is sealed at rest and resumes after a lock or a relaunch; a local attachment send is shown as waiting or not sent, never as a failed download.
- Onboarding fixes: one back control per step, the new account opens after the permission step, the account-created step follows `account.status` until the account is live, and the whole account row opens or unlocks the account.
- After an unlock the screens that were open when the account was locked are reopened.
- Backup shows the progress of a running job while the screen is open.
- Secret entry fields are presented to accessibility services as edit fields.
- A new group's conversation opens by the id its row names.
- Opt-in real-run suite and its manual (`docs/realrun.md`): every machine, device and path is a setting; there are no personal or host defaults. The `realrun` build type is absent from release builds.
- Repository clean-up: the README describes the app and its modules, the manuals no longer refer to a private workspace, and design-token metadata is neutral.

## 0.2.0 - 2026-11-16

First release under the shared Ramflux product version (all repos move together).
Changes since 0.1.0, at a high level:

- Android custody: account keys now stay in the device's secure custody, and the app waits for the secure store before showing private data.
- Generation-1 messaging is supported: the app speaks the new message format and delivery path.
- Contact safety numbers can be verified; edit conflicts are detected rather than overwritten.
- Settings now shows the app version and build number ("Version 0.2.0 (build 2)"), in English and Simplified Chinese.

The version lives in `version.properties`; it follows the shared product version line.
